# 技能创建器

用于创建新技能并迭代改进它们的技能。

从高层次来看，创建技能的过程是这样的：

- 决定你想要技能做什么以及它应该如何大致做到
- 编写技能草稿
- 创建一些测试提示并在有技能的 claude 上运行它们
- 帮助用户定性和定量地评估结果
  - 当运行在后台发生时，如果没有评估则起草一些定量评估（如果有一些，你可以按原样使用或如果你觉得需要更改而修改它们）。然后向用户解释它们（或者如果已经存在，解释已经存在的）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户显示结果供他们查看，也让他们看看定量指标
- 根据用户对结果的评估重写技能（也根据定量基准中出现的任何明显缺陷）
- 重复直到满意
- 扩大测试集并再次尝试更大规模

当使用此技能时，你的工作是弄清楚用户在流程中的哪个阶段，然后帮助他们推进这些阶段。例如，也许他们说"我想为 X 制作一个技能"。你可以帮助缩小他们想要的含义、编写草稿、编写测试用例、弄清楚他们想要如何评估、运行所有提示，并重复。

另一方面，也许他们已经有技能草稿。在这种情况下，你可以直接进入评估/迭代循环。

当然，你应该始终保持灵活，如果用户说"我不需要运行一堆评估，只是随意聊聊"，你可以那样做。

然后在技能完成后（但顺序又是灵活的），你也可以运行技能描述改进器，我们有一个单独的脚本，来优化技能的触发。

准备好了？开始吧。

## 与用户沟通

技能创建器可能被对编程术语熟悉程度差异很大的用户使用。如果你没有听说过（你怎么能听说，它只是最近才开始），现在有一种趋势，Claude 的力量激发了水管工打开他们的终端，父母和祖父母谷歌"如何安装 npm"。另一方面，大多数用户可能相当精通电脑。

所以请注意上下文线索以理解如何措辞你的沟通！在默认情况下，给你一些概念：

- "evaluation" 和 "benchmark" 是边缘的，但可以
- 对于 "JSON" 和 "assertion"，你想看到用户严肃的线索表明他们知道这些东西是什么，然后再使用而不解释它们

如果你不确定用户是否会理解，可以简要解释术语，也可以用简短定义澄清你不确定的术语。

## 创建一个技能

### 捕捉意图

首先理解用户的意图。当前的对话可能已经包含用户想要捕获的工作流程（例如他们说"把这个变成技能"）。如果是这样，首先从对话历史中提取答案 — 使用的工具、步骤序列、用户做的更正、观察到的输入/输出格式。用户可能需要填补空白，并应在进入下一步之前确认。

1. 这个技能应该让 Claude 做什么？
2. 什么时候应该触发？（什么用户措辞/上下文）
3. 期望的输出格式是什么？
4. 我们应该设置测试用例来验证技能工作吗？对于有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流程步骤），测试用例有益。对于有主观输出的技能（写作风格、艺术），通常不需要。

### 面试和研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准和依赖的细节。在写测试提示之前先把这个部分弄清楚。

检查可用的 MCP — 如果对研究有用（搜索文档、查找类似技能、查找最佳实践），如果有子代理则通过子代理并行研究，否则内联研究。准备好上下文以减少用户负担。

### 编写 SKILL.md

根据用户面试，填写以下组件：

- **name**：技能标识符
- **description**：何时触发、做什么。这是主要触发机制 — 包括技能做什么和何时使用的特定上下文。所有"何时使用"信息都在这里，不在正文。注：目前 Claude 有"触发不足"技能的倾向 — 为此，请把技能描述写得"稍微有推动性"。例如，不要写"如何构建一个简单的快速仪表板来显示内部 Anthropic 数据"，你可以写"如何构建一个简单的快速仪表板来显示内部 Anthropic 数据。每当用户提到仪表板、数据可视化、内部指标，或想要显示任何类型的公司数据时，确保使用此技能，即使他们没有明确要求'仪表板'。"
- **compatibility**：必需工具、依赖项（可选，很少需要）
- **技能的其他部分 :)**

### 技能写作指南

#### 技能的组成部分

```
skill-name/
├── SKILL.md (必填)
│   ├── YAML frontmatter (name, description 必填)
│   └── Markdown 说明
└── 捆绑资源 (可选)
    ├── scripts/    - 用于确定性/重复任务的可执行代码
    ├── references/ - 根据需要加载到上下文的文档
    └── assets/     - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

技能使用三级加载系统：
1. **元数据**（name + description）— 始终在上下文中（~100 字）
2. **SKILL.md 正文** — 技能触发时在上下文中（理想 <500 行）
3. **捆绑资源** — 根据需要（无限，脚本可以在不加载的情况下执行）

这些字数是大致的，如果你需要可以随意更长。如果你接近这个限制，添加额外的层次结构以及关于使用技能的模型下一步应该去哪里跟进的明确指针。

**关键模式：**
- 保持 SKILL.md 少于 500 行；如果你接近这个限制，添加额外的层次结构以及关于模型应该去哪里跟进的明确指针
- 从 SKILL.md 明确引用文件，并指导何时阅读它们
- 对于大型参考文件（>300 行），包含目录

**领域组织**：当技能支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md (工作流程 + 选择)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关参考文件。

#### 无惊喜原则

不用说，技能不能包含恶意软件、利用代码或任何可能损害系统安全的内容。技能的内容如果被描述，不应该让用户惊讶于其意图。不要配合创建误导性技能或旨在促进未经授权访问、数据泄露或其他恶意活动的技能。像"扮演 XYZ"的角色扮演是可以的。

#### 写作模式

在说明中优先使用祈使语气。

**定义输出格式** — 你可以这样做：
```markdown
## 报告结构
始终使用这个确切模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式** — 包含示例很有用。你可以这样格式化（但如果"输入"和"输出"在示例中，你可能想稍微偏离）：
```markdown
## 提交消息格式
**示例 1：**
输入：使用 JWT 令牌添加用户认证
输出：feat(auth): 实现基于 JWT 的认证
```

### 写作风格

尝试向模型解释为什么事情重要，而不是用老式的 MUST 来强制。使用心理理论，尝试让技能通用而不是非常针对特定示例。先写草稿，然后用新眼光看它并改进它。

### 测试用例

写完技能草稿后，想出 2-3 个现实测试提示 — 真实用户实际会说的那种。与用户分享：[你不必使用完全相同的语言]"这里是我想尝试的几个测试用例。这些看起来对吗，还是你想添加更多？"然后运行它们。

将测试用例保存到 `evals/evals.json`。现在先不写断言 — 只是提示。你会在下一步中起草断言，同时运行正在进行。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "预期结果描述",
      "files": []
    }
  ]
}
```

参见 `references/schemas.md` 获取完整模式（包括你稍后添加的 `assertions` 字段）。

## 运行和评估测试用例

本节是一个连续序列 — 不要中途停止。不要使用 `/skill-test` 或任何其他测试技能。

将结果放入 `<skill-name>-workspace/` 作为技能目录的同级。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），在其中每个测试用例得到一个目录（`eval-0/`、`eval-1/` 等）。不要提前创建所有这些 — 随着进行创建目录。

### 步骤 1：在同一轮中生成所有运行（有技能和无技能的基线）

对于每个测试用例，在同一轮中生成两个子代理 — 一个有技能，一个没有。这很重要：不要先生成有技能的运行然后稍后回来生成基线。立即全部启动，这样它们都大约同时完成。

**有技能运行：**

```
执行此任务：
- 技能路径：<path-to-skill>
- 任务：<eval prompt>
- 输入文件：<eval 文件（如果有）或 "none">
- 将输出保存到：<workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 要保存的输出：<用户关心的内容 — 例如 ".docx 文件"、"最终 CSV">
```

**基线运行**（相同提示，但基线取决于上下文）：
- **创建新技能**：完全无技能。相同提示，无技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。在编辑之前，快照技能（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后将基线子代理指向快照。保存到 `old_skill/outputs/`。

为每个测试用例编写 `eval_metadata.json`（断言现在可以为空）。给每个评估一个描述性名称，基于它测试什么 — 不要只是 "eval-0"。也用这个名称作为目录。如果此迭代使用新的或修改的评估提示，为每个新的评估目录创建这些文件 — 不要假设它们从前一个迭代继承。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "用户的任务提示",
  "assertions": []
}
```

### 步骤 2：当运行进行时，起草断言

不要只是等待运行完成 — 你可以富有成效地利用这段时间。为每个测试用例起草定量断言并向用户解释。如果 `evals/evals.json` 中已有断言，审查它们并解释它们检查什么。

好的断言是客观可验证的，并且有描述性名称 — 它们应该在基准查看器中清晰阅读，这样扫一眼结果的人立即理解每个检查什么。有主观输出的技能（写作风格、设计质量）更适合定性评估 — 不要在需要人类判断的东西上强制断言。

更新 `eval_metadata.json` 文件和 `evals/evals.json` 以及断言一旦起草。也向用户解释他们将在查看器中看到什么 — 定性输出和定量基准。

### 步骤 3：当运行完成时，捕获计时数据

当每个子代理任务完成时，你收到包含 `total_tokens` 和 `duration_ms` 的通知。立即将此数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获此数据的唯一机会 — 它通过任务通知传来，不会持久化在其他地方。随着每个通知到达处理它，而不是试图批量处理。

### 步骤 4：评分、聚合并启动查看器

一旦所有运行完成：

1. **评分每个运行** — 生成评分子代理（或内联评分），读取 `agents/grader.md` 并针对输出评估每个断言。将结果保存到每个运行目录中的 `grading.json`。grading.json 期望数组必须使用字段 `text`、`passed` 和 `evidence`（不是 `name`/`met`/`details` 或其他变体）— 查看器依赖这些确切字段名称。对于可以编程检查的断言，编写并运行脚本而不是肉眼检查 — 脚本更快、更可靠，可以跨迭代重用。

2. **聚合为基准** — 从技能创建器目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这产生带有 pass_rate、时间和代币的 `benchmark.json` 和 `benchmark.md`，带有均值 ± 标准差和增量。如果手动生成 benchmark.json，参见 `references/schemas.md` 获取查看器期望的确切模式。
   将每个有技能的版本放在其基线对应物之前。

3. **做分析师通过** — 读取基准数据并揭示聚合统计可能隐藏的模式。参见 `agents/analyzer.md`（"分析基准结果"部分）了解要查找什么 — 诸如总是通过的断言之类的东西（无区分力）、高方差评估（可能不稳定）以及时间/代币权衡。

4. **启动查看器** 带有定性和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于迭代 2+，也传递 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork/无头环境：** 如果 `webbrowser.open()` 不可用或环境没有显示器，使用 `--static <output_path>` 写入独立 HTML 文件而不是启动服务器。用户点击"提交所有评论"后，反馈将下载为 `feedback.json` 文件。下载后，将 `feedback.json` 复制到工作区目录，以便下一次迭代拾取。

   注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **告诉用户** 类似于："我在你的浏览器中打开了结果。有两个标签 — '输出' 让你点击每个测试用例并留下反馈，'基准' 显示定量比较。你完成后，回来这里告诉我。"

### 用户在查看器中看到的内容

"输出"标签一次显示一个测试用例：
- **提示**：给出的任务
- **输出**：技能产生的文件，尽可能内联渲染
- **上一个输出**（迭代 2+）：显示上一次迭代输出的折叠部分
- **正式评分**（如果运行了评分）：显示断言通过/失败情况的折叠部分
- **反馈**：随着输入自动保存的文本框
- **上一个反馈**（迭代 2+）：他们上次评论的内容，显示在文本框下方

"基准"标签显示统计摘要：每个配置 pass_rate、时间和代币使用，带每个评估分解和分析师观察。

导航通过上一个/下一个按钮或箭头键。完成后，点击"提交所有评论"将所有反馈保存到 `feedback.json`。

### 步骤 5：阅读反馈

当用户告诉你完成后，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，我喜欢这个", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈意味着用户认为没问题。将改进重点放在用户有具体投诉的测试用例上。

完成后杀死查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。你已经运行了测试用例，用户已经审查了结果，现在你需要根据他们的反馈使技能变得更好。

### 如何思考改进

1. **从反馈中泛化。** 这里发生的大画面事情是，我们正在尝试创建可以跨许多不同提示使用一百万次（也许字面上，也许更多谁知道）的技能。在这里，你和用户只是在一次又一次地迭代几个例子，因为它有助于加快速度。用户了解这些例子，用户可以快速评估新输出。但如果技能你和用户共同开发的只适用于那些例子，它是无用的。不要进行棘手的过度拟合更改，或压迫性的限制性 MUSTS，如果有固执的问题，你可以尝试分支并使用不同的隐喻，或推荐不同的工作模式。尝试相对便宜，也许你会碰上很棒的东西。

2. **保持提示精简。** 删除没有发挥作用的权重的东西。确保阅读了记录，而不仅仅是最终输出 — 如果看起来技能让模型浪费大量时间做不高效的事情，你可以尝试删除技能中让它那样做的部分，然后看看会发生什么。

3. **解释原因。** 尝试努力解释为什么你要模型做的每件事背后的原因。今天的 LLM 很聪明。他们有很好的心理理论，当给出好的框架时，可以超越僵化指令，真正发挥作用。即使用户反馈是简短或沮丧的，尝试真正理解任务以及用户为什么写他们写的内容，然后真正理解他们写的内容，然后将这种理解转化为说明。如果发现自己使用全大写 ALWAYS 或 NEVER，这是一个黄色标志 — 如果可能，重新框架并解释原因，这样模型理解为什么你要它做的是重要的。这是一个更人性化、更强大、更有效的方法。

4. **寻找跨测试用例的重复工作。** 从测试运行中阅读记录，并注意子代理是否都独立写了类似的辅助脚本或对某事物采取了相同的多步骤方法。如果所有 3 个测试用例导致子代理写了 `create_docx.py` 或 `build_chart.py`，这是强烈信号，技能应该捆绑该脚本。写一次，放入 `scripts/`，告诉技能使用它。这节省了每次未来调用重新发明轮子。

这项任务非常重要（我们正在尝试每年创造数十亿美元的经济价值！）你的思考时间不是瓶颈；慢慢来，真正思考。我建议写一个修订草稿，然后用新眼光看它并改进。真正尽最大努力进入用户的脑海，理解他们想要和需要什么。

### 迭代循环

改进技能后：

1. 应用你的改进到技能
2. 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录，包括基线运行。如果创建新技能，基线始终是 `without_skill`（无技能）— 这在迭代中保持不变。如果改进现有技能，使用你的判断什么作为基线有意义：用户带来的原始版本，或上一次迭代。
3. 启动带有 `--previous-workspace` 指向上一迭代的审查器
4. 等待用户审查并告诉你完成了
5. 读取新反馈，再次改进，重复

继续直到：
- 用户说他们满意
- 反馈都是空的（一切看起来不错）
- 你没有取得有意义的进展

## 高级：盲比较

对于想要更严格比较技能两个版本之间的情况（例如用户问"新版本实际上更好吗？"），有一个盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 了解详情。基本思想是：给两个输出给独立代理，不告诉它哪个是哪个，让它判断质量。然后分析为什么赢家赢了。

这是可选的，需要子代理，大多数用户不需要。人类审查循环通常就足够了。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用技能的主要机制。创建或改进技能后，提供优化描述以获得更好的触发准确性。

### 步骤 1：生成触发评估查询

创建 20 个评估查询 — 应该触发和不应该触发的混合。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

查询必须现实且是 Claude Code 或 Claude.ai 用户实际会输入的内容。不是抽象请求，而是具体且有相当多细节的请求。例如，文件路径、关于用户工作或情况的个人上下文、列名和值、公司名称、URL。一点背景故事。有些可能是小写或包含缩写或口语。可能包含不同长度，专注于边缘情况而不是使它们显而易见（用户将有机会批准）。

不好：`"格式化此数据"`、`"从 PDF 提取文本"`、`"创建图表"`

好：`"好的，我老板刚发给我这个 xlsx 文件（在我的下载里，叫什么类似 'Q4 销售最终版 FINAL v2.xlsx'），她想让我添加一列，显示利润率为百分比。收入在 C 列，成本在 D 列我想"`

对于**应该触发**的查询（8-10），考虑覆盖率。你想要同一意图的不同表达 — 一些正式，一些口语。包括用户没有明确命名技能或文件类型但显然需要它的情况。添加一些不常见的用例以及此技能与其他技能竞争但应该获胜的情况。

对于**不应该触发**的查询（8-10），最有价值的是near-misses — 分享关键词或概念但实际需要不同东西的查询。思考相邻领域、模糊措辞，朴素关键词匹配会触发但不应该的情况，以及查询涉及技能做的事情但在另一种工具更合适的上下文中。

要避免的关键：不要使不应该触发的查询明显无关。"为 PDF 技能作为负面测试写一个 fibonacci 函数"太容易 — 它不测试任何东西。负面情况应该真正棘手。

### 步骤 2：与用户审查

使用 HTML 模板向用户展示评估集供审查：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（周围没有引号 — 它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能的当前描述
3. 写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击"导出评估集"
5. 文件下载到 `~/Downloads/eval_set.json` — 检查下载文件夹以防有多个（例如 `eval_set (1).json`）

此步骤很重要 — 坏的评估查询导致坏的描述。

### 步骤 3：运行优化循环

告诉用户："这需要一些时间 — 我会在后台运行优化循环并定期检查它。"

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中驱动当前会话的模型 ID，以便触发测试匹配用户实际体验的内容。

当它运行时，周期性 tail 输出以向用户提供它在哪次迭代以及分数看起来怎样的更新。

这自动处理完整的优化循环。它将评估集拆分为 60% 训练和 40% 保留测试，评估当前描述（运行每个查询 3 次以获得可靠的触发率），然后调用 Claude 根据失败情况提出改进。它在训练和测试上重新评估每个新描述，迭代最多 5 次。完成后，它在浏览器中打开 HTML 报告，显示每次迭代的结果并返回带有 `best_description` 的 JSON — 按测试分数而非训练分数选择以避免过拟合。

### 技能触发如何工作

理解触发机制有助于设计更好的评估查询。技能出现在 Claude 的 `available_skills` 列表中，带有它们的名称和描述，Claude 根据该描述决定是否咨询技能。需要知道的重要事情是，Claude 只为它不能轻易自行处理的任务咨询技能 — 简单的、一步的查询如"读取此 PDF"可能不会触发技能，即使描述完全匹配，因为 Claude 可以直接使用基本工具处理。复杂的、多步骤的或专业化查询，当描述匹配时可靠地触发技能。

这意味着你的评估查询应该足够实质，以便 Claude 实际上会受益于咨询技能。像"读取文件 X"这样的简单查询是糟糕的测试用例 — 无论描述质量如何，它们都不会触发技能。

### 步骤 4：应用结果

从 JSON 输出中获取 `best_description` 并更新技能的 SKILL.md frontmatter。向用户展示前后对比并报告分数。

### 打包和呈现（仅当 `present_files` 工具可用时）

检查你是否有权访问 `present_files` 工具。如果没有，跳过此步骤。如果有，打包技能并向用户呈现 .skill 文件：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，指向用户生成的 .skill 文件路径，以便他们可以安装它。

## Claude.ai 特定说明

在 Claude.ai 中，核心工作流程相同（草稿 → 测试 → 审查 → 改进 → 重复），但因为 Claude.ai 没有子代理，一些机制改变了。以下是要适应的内容：

**运行测试用例**：没有子代理意味着没有并行执行。对于每个测试用例，读取技能的 SKILL.md，然后按照其说明完成测试提示自己。一个接一个地做。这不如独立子代理（你写了技能你也在运行它，所以你有完整上下文），但它是有效的健全检查 — 人类审查步骤补偿。没有基线运行 — 只需使用技能完成请求的任务。

**审查结果**：如果你无法打开浏览器（例如 Claude.ai 的 VM 没有显示器，或者你在远程服务器上），完全跳过浏览器审查器。相反，直接在对话中呈现结果。对于每个测试用例，显示提示和输出。如果输出是用户需要看的文件（如 .docx 或 .xlsx），保存到文件系统并告诉他们在哪里以便下载和检查。内联请求反馈："看起来怎么样？有什么你想改变的吗？"

**基准测试**：跳过定量基准测试 — 它依赖基线比较，在没有子代理的情况下没有意义。专注于用户来自审查的定性反馈。

**迭代循环**：相同 — 改进技能，重新运行测试用例，请求反馈 — 只是中间没有浏览器审查器。你仍然可以在文件系统上组织迭代目录（如果你有的话）。

**描述优化**：本节需要 `claude` CLI 工具（具体是 `claude -p`），仅在 Claude Code 中可用。在 Claude.ai 上跳过。

**盲比较**：需要子代理。在 Claude.ai 上跳过。

**打包**：`package_skill.py` 脚本在有 Python 和文件系统的任何地方工作。在 Claude.ai 上，你可以运行它，用户可以下载生成的 .skill 文件。

**更新现有技能**：用户可能要求你更新现有技能，而非创建新的。在这种情况下：
- **保留原始名称。** 注意技能的目录名称和 `name` frontmatter 字段 — 原样使用。例如，如果安装的技能是 `research-helper`，输出 `research-helper.skill`（而非 `research-helper-v2`）。
- **在可写位置复制后再编辑。** 安装的技能路径可能是只读的。复制到 `/tmp/skill-name/`，在那里编辑，然后从副本打包。
- **如果手动打包，先在 `/tmp/` 中暂存**，然后复制到输出目录 — 直接写入可能因权限失败。

## Cowork 特定说明

如果你在 Cowork，需要知道的主要事情是：

- 你有子代理，所以主要工作流程（并行生成测试用例、运行基线、评分等）都有效。（但是，如果你遇到严重的超时问题，按顺序运行测试提示而不是并行也可以。）
- 你没有浏览器或显示器，所以在生成评估查看器时，使用 `--static <output_path>` 写入独立 HTML 文件而不是启动服务器。然后提供一个链接，用户可以点击在浏览器中打开 HTML。
- 由于某种原因，Cowork 设置似乎让 Claude 不愿在运行测试后生成评估查看器，所以只是重申：无论你在 Cowork 还是在 Claude Code，在运行测试后，你应该始终生成评估查看器供人类在你自己评估输入之前查看，使用 `generate_review.py`（不是编写自己的花哨 html 代码）。提前致歉，但我会用全大写：**在评估输入之前生成评估查看器**。你想让他们尽快看到例子！
- 反馈工作方式不同：因为没有运行中的服务器，查看器的"提交所有评论"按钮会将 `feedback.json` 下载为文件。然后你可以从那里读取（你可能必须先请求访问）。
- 打包工作 — `package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）应该在 Cowork 中正常工作，因为它使用 `claude -p` 通过子进程，而不是浏览器，但请保存到你完全完成制作技能并且用户同意它状况良好之后。
- **更新现有技能**：用户可能要求你更新现有技能，而非创建新的。按照上面 Claude.ai 部分中的更新指导。
