# 系统文献综述技能

## 概述

本技能对研究主题的多篇学术论文进行结构化的**系统文献综述（SLR）**。给定主题查询，它搜索 arXiv、并行从每篇论文中提取结构化元数据（研究问题、方法论、关键发现、局限性）、综合整个集合的主题，并在最终报告中发出带有一致引用的内容。

**与 `academic-paper-review` 的区别：** 那项技能做单篇论文的深度同行评审。此技能做多篇论文的广度优先综合。如果用户给你一篇论文 URL 并要求"审查这篇论文"，路由到 `academic-paper-review` 而不是。

## 何时使用此技能

当用户想要以下任何内容时使用此技能：

- 关于某个主题的文献调查（"调查 transformer 注意力变体"、"综述扩散模型的文献"）
- 多篇论文的综合（"最近关于 X 的论文说什么"、"比较 Y 主题论文的方法论"）
- 带一致引用格式的系统综述（"以 APA 格式对 Z 做 SLR"）
- 关于某个主题的带注释书目
- 一个领域在一段时间内的研究趋势概述

**不要**在以下情况使用此技能：

- 用户只提供一篇论文并要求审查（使用 `academic-paper-review`）
- 用户提出不需要综合多个来源的事实问题（直接回答）
- 用户想要没有学术严谨性的常规网络研究（使用标准网络搜索）

## 工作流程

工作流程有五个阶段。按顺序遵循。

### 第一阶段：规划

在任何检索之前，向用户确认以下内容。如果任何不清楚，问**一个**涵盖缺失部分的问题。不要一次问一个问题。

- **主题**：用简单英语描述的研究领域（例如"transformer 注意力变体"）。
- **范围**：多少篇论文（默认 20，硬上限 50），可选时间窗口（例如"过去 2 年"），可选 arXiv 类别（例如 `cs.CL`、`cs.CV`）。
- **引用格式**：APA、IEEE 或 BibTeX（如果用户未指定且似乎在为特定场所写作，默认为 APA）。
- **输出位置**：保存最终报告的位置（默认 `/mnt/user-data/outputs/`）。

如果用户说"50+ 篇论文"，礼貌地将其上限为 50 并解释综合质量会很快下降 — 对于更大的调查，他们应该按子主题分割。

### 第二阶段：搜索 arXiv

调用捆绑的搜索脚本。**不要**尝试用其他方式抓取 arXiv，也**不要**编写自己的 HTTP 客户端 — 此脚本正确处理 URL 编码、Atom XML 解析和 ID 规范化。

```bash
python /mnt/skills/public/systematic-literature-review/scripts/arxiv_search.py \
  "<topic>" \
  --max-results <N> \
  [--category <cat>] \
  [--sort-by relevance] \
  [--start-date YYYY-MM-DD] \
  [--end-date YYYY-MM-DD]
```

**重要 — 提取 2-3 个核心关键词后再搜索。** 不要将用户的完整主题描述作为查询传递。在调用脚本之前，在精神上将主题缩减为其 2-3 个最基本术语。删除限定词如"在计算机视觉中"、"用于 NLP"、"变体"、"最近的" — 那些属于 `--category` 或 `--start-date`，而非查询字符串。

**查询措辞 — 保持简短。** 脚本将多词查询包装在双引号中进行短语匹配。这意味着：

- `"diffusion models"` → 搜索确切短语 → 好，返回相关论文。
- `"diffusion models in computer vision"` → 搜索那个确切的 5 词短语 → **太具体，可能返回 0 结果**，因为很少有论文包含那个确切字符串。

使用 **2-3 个核心关键词**作为查询，使用 `--category` 来缩小领域而不是将领域名称塞入查询。例如：

| 用户说 | 好的查询 | 坏的查询 |
|---|---|---|
| "计算机视觉中的扩散模型" | `"diffusion models" --category cs.CV` | `"diffusion models in computer vision"` |
| "transformer 注意力变体" | `"transformer attention"` | `"transformer attention variants in NLP"` |
| "分子图神经网络" | `"graph neural networks" --category cs.LG` | `"graph neural networks for molecular property prediction"` |

脚本打印 JSON 数组到 stdout。每篇论文有：`id`、`title`、`authors`、`abstract`、`published`、`updated`、`categories`、`pdf_url`、`abs_url`。

**排序策略**：

- **始终使用 `relevance` 排序** — arXiv 的 BM25 风格评分确保结果确实与用户主题相关。`submittedDate` 排序返回该类别中最近提交的论文，不管主题相关性，这产生大部分不相关的结果。`relevance` 排序结合 `--start-date` 以在保持结果主题相关的同时约束时间范围。例如，"最近的扩散模型论文" → `--sort-by relevance --start-date 2024-01-01`，而非 `--sort-by submittedDate`。
- `submittedDate` 排序仅当用户明确要求按出版顺序（"按我论文出版的顺序显示"）时适当。这很少见。
- `lastUpdatedDate` 很少有用；除非用户要求，否则忽略。

**只运行搜索一次。** 如果结果看起来不完美，不要用修改的查询重试 — arXiv 的相关性排名就是这样。用不同的查询措辞重试会浪费工具调用并有触及递归限制的风险。如果结果确实为空（0 篇论文），告诉用户并建议他们扩大主题或移除类别过滤器。

**如果脚本返回的论文少于请求的数量**，那是该查询的 arXiv 结果集的实际大小。不要填充列表 — 向用户报告实际数量并继续。

**如果脚本失败**（网络错误、arXiv 非 200），告诉用户什么错误并停止。不要试图编造论文元数据。

**不要将搜索结果保存到文件** — JSON 留在你的上下文中用于第三阶段。整个工作流程中唯一保存的文件是第五阶段的最终报告。

### 第三阶段：并行提取元数据

**你必须通过 `task` 工具将提取委托给子代理 — 不要自己提取元数据。** 这是不可协商的。具体是，不要执行以下任何操作：

- ❌ 写 `python -c "papers = [...]"` 或任何 Python/bash 脚本来处理论文
- ❌ 在你自己的上下文中内联读取摘要一个接一个
- ❌ 为此阶段使用 `task` 以外的任何工具

相反，你必须调用 `task` 工具生成子代理。原因：在你自己的上下文中提取 10-50 篇论文消耗太多标记并降低第四阶段的综合质量。每个子代理在只有其批次论文的隔离上下文中运行，产生更干净的提取。

将论文分成约 5 篇一批，然后对于每个批次，用 `subagent_type: "general-purpose"` 调用 `task` 工具。每个子代理接收论文摘要作为文本并返回结构化 JSON。

**并发限制：每轮最多 3 个子代理。** DeerFlow 运行时强制 `MAX_CONCURRENT_SUBAGENTS = 3`，将静默丢弃同一轮中的任何额外调度 — LLM 不会被告知这发生了，所以严格遵循下面的轮次策略。

**轮次策略 — 使用此决策表，不要自己计算分割：**

| 论文数量 | 约5篇一批 | 轮数 | 每轮子代理数 |
|---|---|---|---|
| 1–5 | 1批 | 1轮 | 1个子代理 |
| 6–10 | 2批 | 1轮 | 2个子代理 |
| 11–15 | 3批 | 1轮 | 3个子代理 |
| 16–20 | 4批 | 2轮 | 3 + 1 |
| 21–25 | 5批 | 2轮 | 3 + 2 |
| 26–30 | 6批 | 2轮 | 3 + 3 |
| 31–35 | 7批 | 3轮 | 3 + 3 + 1 |
| 36–40 | 8批 | 3轮 | 3 + 3 + 2 |
| 41–45 | 9批 | 3轮 | 3 + 3 + 3 |
| 46–50 | 10批 | 4轮 | 3 + 3 + 3 + 1 |

**永远不要在同一轮中调度超过 3 个子代理。** 当一行说"2轮 (3 + 1)"，意思是：第一轮并行调度 3 个子代理，等待所有 3 个完成，然后第二轮调度 1 个子代理。轮次在主代理级别严格顺序执行。

如果论文数量落在行之间（例如 23 篇论文），向上舍入到下一行的布局，但只调度你实际需要的批次 — 决策表给你形状，不是硬性规定。

**在主代理级别进行批处理**：你已经有了第二阶段每篇论文的摘要，所以每个子代理接收纯文本输入。子代理不应需要访问网络或沙箱 — 它们唯一的工作是读取文本并返回 JSON。不要要求子代理重新运行 `arxiv_search.py`；那会浪费标记并有速率限制风险。

**每个子代理接收的内容**，作为结构化提示：

```
执行此任务：从以下 arXiv 论文中提取结构化元数据和关键发现。

论文：
[论文 1]
arxiv_id: 1706.03762
title: Attention Is All You Need
authors: Ashish Vaswani, Noam Shazeer, ...
published: 2017-06-12
abstract: <完整摘要文本>

[论文 2]
arxiv_id: ...
...

对于每篇论文，返回带有这些字段的 JSON 对象：
- arxiv_id (字符串)
- title (字符串)
- authors (字符串列表)
- published_date (字符串, YYYY-MM-DD)
- research_question (1句话, 论文解决什么问题)
- methodology (1-2句话, 他们如何解决它)
- key_findings (3-5个要点, 他们实际发现了什么)
- limitations (1-2句话, 他们承认什么或明显缺少什么)

以 JSON 数组返回结果，每篇论文一个对象，与输入顺序相同。不要在 JSON 之外包含任何文本 — 无前言，无 markdown 围栏，只是数组。
```

**解析子代理结果**：任务工具返回带有固定前缀如 `Task Succeeded. Result: [...JSON...]` 的字符串。在尝试解析 JSON 之前，剥离 `Task Succeeded. Result: ` 前缀（或者 `Task failed.` / `Task timed out.` 前缀）。如果批次失败或返回不可解析的 JSON，记录它，注明哪些论文受影响，并继续处理剩余批次 — 不要因一个坏批次而使整个综合失败。

所有轮次完成后，将每批数组扁平化为单个论文元数据对象列表，保持顺序。

### 第四阶段：综合和格式化

现在生成最终 SLR 报告。这里发生两件事：跨论文综合（主题分析）和引用格式化。

**跨论文综合**：报告必须做的不仅仅是列出论文。至少识别：

- **主题**：集合中 3-6 个反复出现的研究方向、方法或问题框架。
- **趋同**：多篇论文同意的发现。
- **分歧**：论文得出不同结论或使用不兼容方法论的地方。
- **差距**：集体文献尚未解决的问题（通常在"局限性"字段中明确说明）。

如果论文集太小或太异构以支持主题综合（例如，5 篇关于完全不同子主题的论文），在报告中明确说明 — 不要强制不存在的的主题。

**引用格式化**：确切格式取决于用户偏好。只阅读**与用户请求格式匹配的模板文件**，而非全部三个：

- [APA 模板](templates/apa.md) — APA 第7版。社会科学和大多数 CS 期刊的默认值。当用户请求 APA 或未指定格式时使用。
- [IEEE 模板](templates/ieee.md) — IEEE 数字引用。当用户针对 IEEE 会议或期刊，或明确请求 IEEE 时使用。
- [BibTeX 模板](templates/bibtex.md) — BibTeX 条目。当用户提到 BibTeX、LaTeX 或想要机器可读引用时使用。**重要**：arXiv 论文引用为 `@misc`，而非 `@article` — BibTeX 模板明确涵盖此。

每个模板既包含引用规则，也包含完整报告结构（执行摘要、主题、每篇论文注释、参考文献、方法论部分）。严格遵循模板的结构作为报告正文，然后从第三阶段元数据填入内容。

### 第五阶段：保存和呈现

将完整报告保存到 `/mnt/user-data/outputs/slr-<topic-slug>-<YYYYMMDD>.md`，其中 `<topic-slug>` 是主题的小写连字符版本（例如 `transformer-attention`）。然后调用 `present_files` 工具以及该路径，以便用户可以下载。

**在聊天消息中**，显示简短预览，以便用户立即看到价值而无需打开文件：

1. **执行摘要** — 报告顶部 3-5 句段落，原样呈现。
2. **主题列表** — 你在第四阶段综合中识别的主题的要点列表（只需主题名称 + 一行解释，不是完整主题章节）。
3. **论文数量 + 文件指针** — 例如，"完整报告包含 20 篇论文、每篇论文注释和格式化引用，保存到 `slr-transformer-attention-20260409.md`。"

**不要**内联转储完整的 2000+ 字报告 — 每篇论文注释、参考文献和方法论属于文件。预览是为了让用户一目了然地判断报告并决定是否打开。

## 示例

**示例 1：典型 SLR 请求**

用户："对最近的 transformer 注意力变体进行系统文献综述，20 篇论文，APA 格式。"

你的流程：
1. 第一阶段：确认主题（transformer 注意力变体）、范围（20 篇论文，默认时间窗口）、格式（APA）。如果缺少内容只问一个澄清问题（例如"任何特定时间窗口，还是我默认为过去 3 年？"）。
2. 第二阶段：`arxiv_search.py "transformer attention" --max-results 20 --sort-by relevance --start-date 2023-01-01`。
3. 第三阶段：20 篇论文 → 第1轮 = 3 个子代理 × 5 篇论文 = 15 篇覆盖，第2轮 = 1 个子代理 × 5 篇论文 = 5 篇覆盖。聚合。
4. 第四阶段：读取 `templates/apa.md`，使用其结构编写报告，从第三阶段元数据填入主题 + 每篇论文注释。
5. 第五阶段：保存到 `slr-transformer-attention-20260409.md`，调用 `present_files`。

**示例 2：小规模请求与歧义**

用户："为我调查几篇关于扩散模型的论文。"

你的流程：
1. 第一阶段："几篇"是歧义的。只问一个问题："你想要多少篇论文 — 10、20 还是 30？还有引用格式偏好（APA 是默认值）？"
2. 用户回复"10 篇，BibTeX"。
3. 第二阶段：`arxiv_search.py "diffusion models" --max-results 10 --category cs.CV`。
4. 第三阶段：10 篇论文 → 单轮，2 个子代理 × 5 篇论文。
5. 第四阶段：读取 `templates/bibtex.md`，用 `@misc` 条目格式化（而非 `@article`）。
6. 第五阶段：保存并呈现。

**示例 3：超出范围请求**

用户："这是 (https://arxiv.org/abs/1706.03762) 一篇论文。你能审查它吗？"

这是单篇论文同行评审，不是文献调查。不要使用此技能。改为路由到 `academic-paper-review`。

## 注意事项

- **前提：`subagent_enabled` 必须为 `true`**。第三阶段需要 `task` 工具进行并行元数据提取。此工具仅在运行时配置中 `config.configurable.subagent_enabled` 设置为 `true` 时加载。没有它，`task` 工具将不会出现在可用工具中，第三阶段无法按设计执行。
- **仅 arXiv，按设计**。此技能不查询 Semantic Scholar、PubMed 或 Google Scholar。arXiv 覆盖了大多数 CS/ML/物理/数学预印本，这是 DeerFlow 用户最常想要调查的。多来源学术搜索属于专用 MCP 服务器，而非此技能内部。
- **论文硬上限 50 篇**。这与第三阶段并发策略挂钩（每轮最多 3 个子代理，每批约 5 篇论文，最多约 3 轮）。大于 50 篇论文的调查综合质量下降，最好按子主题分割。
- **第三阶段需要子代理启用**。此技能的并行提取步骤硬性要求 `task` 工具，仅在运行时 `subagent_enabled=true` 时可用。如果子代理不可用，不要声称执行第三阶段并行计划；而是告诉用户必须启用子代理才能使用完整工作流程，或提供缩小/分割请求为更小的手动评审。
- **子代理结果是字符串，不是对象**。在解析 JSON 之前始终剥离 `Task Succeeded. Result: ` / `Task failed.` / `Task timed out.` 前缀。
- **`id` 字段是裸 arXiv id**（例如 `1706.03762`），不是 URL 也不是带版本后缀的。如果需要，`abs_url` / `pdf_url` 保存完整 URL。
- **综合，而非列出**。最终报告必须识别主题并跨论文比较发现。只列出论文的报告是失败模式 — 如果你找不到主题，改为明确说明而不是伪造。
